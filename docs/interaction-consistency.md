# 互动数据一致性

## 写入与读取

- 原帖子点赞、收藏和原评分服务在 MySQL 事务内维护事实记录、聚合计数和 Outbox 事件。唯一约束与幂等逻辑防止重复累加。
- 原消息链路将 Outbox 发布到 RabbitMQ，消费者删除 Redis 缓存；当前本地配置使用 mesh.local-outbox=true，由发布任务直接执行缓存失效，不需要启动 RabbitMQ。
- 查询缓存未命中时回源 MySQL；缓存故障时按原服务的降级逻辑查询数据库。
- 原浏览量批次同步使用 view_count_flush_batch.batch_id 避免重复入库。Redis 在持久化前丢失仍可能导致部分浏览量损失。

新课程评价与投票通过各自领域表保存，不应把原评分服务的缓存策略等同于所有新课程接口的实现。

## 迁移与环境

新克隆项目使用独立空库，交由 Flyway 从 V001 开始初始化，无需执行旧项目的独立 SQL 补丁。禁止将这套新库迁移直接指向已有生产库。

如果后续恢复 RabbitMQ，需要明确配置 exchange/队列、监听器和连接信息，并关闭本地 Outbox 替代路径。不能只改一个开关就认定消息链路已经联调成功。

## 一致性边界

- MySQL 是点赞/收藏等业务事实的来源，Redis 是缓存。
- Outbox 按至少一次语义处理，消费操作必须保持幂等。
- 缓存与数据库最终一致；失效任务延迟时可能短暂读取旧缓存。
- 失败事件需要监控、重试或人工处理。不要通过清空整个 Redis 实例修复单条业务状态。
